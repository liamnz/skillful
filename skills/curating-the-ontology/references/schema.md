# Record schema

Read this before creating or editing a concept or the manifest by hand. Prefer the
scripts: `new` creates concepts and `vocab new` adds vocabulary. After any hand edit,
run `onto.py validate` (E002 reports schema violations with the field that is wrong).

The ontology lives in `docs/ontology/`:

```
docs/ontology/
  ontology.yaml        # the manifest
  concepts/<id>.yaml   # one file per concept; the file name equals the id
  index.html           # generated by `onto.py build`; never edit it
```

## Who writes what

- **Humans** write every `definition` and decide every `status: defined`, for concepts
  and vocabulary extensions alike. An agent may type a definition only when the human
  dictates it in the conversation, word for word. Git history is the authorship record;
  there are no author fields.
- **Agents** may write `proposal` (rationale and suggested definition), create
  `proposed` stubs with consent, and apply structural fixes with consent.
- **Cardinality** is a domain claim: suggest it with evidence, record it only after a
  human confirms.

## One term per concept

`name` is the single canonical term, used in code, docs and conversation.
`discouraged_terms` exist only so that variants already in circulation (stakeholder
jargon, legacy names, terms an agent invented) can be recognised and redirected. They
are not synonyms to use.

- A term may belong to only one concept, as a name or as a discouraged term (E007).
- A variant that does not map cleanly ("MAU" is narrower than "Active customer") is not
  a discouraged term: it points to a separate concept.
- Code identifiers (column and model names) are never discouraged terms. They belong in
  `implemented_in.symbol`.

## Concept (`concepts/<id>.yaml`)

```yaml
id: active-customer
name: Active customer
kind: entity
status: defined
definition: >
  A customer who has made at least one paid order in the trailing
  90 days, regardless of subscription state.
discouraged_terms:
  - {term: active user, note: "Product team's usage"}
examples: ["A customer whose last paid order was 12 days ago"]
non_examples: ["A customer on a free trial with no paid orders"]
rules: ["Every active customer is a customer."]
relations:
  - {type: is_a, target: customer}
  - {type: has, target: subscription, cardinality: "1:N"}
implemented_in:
  - path: models/marts/dim_customer.sql
    symbol: is_active
    reviewed_at: 3f9c2e1b7a...
open_questions: ["Should refunded orders count?"]
```

| Field | Required | Meaning and rules |
|---|---|---|
| `id` | yes | Kebab-case (`a-z`, `0-9`, single hyphens). Equals the file name (E003). Stable: never rename casually; deprecate and replace instead. |
| `name` | yes | The canonical term. Unique across names and discouraged terms (E007). |
| `kind` | yes | A core kind (`entity`, `event`, `attribute`, `metric`) or a declared kind extension (E005). |
| `status` | yes | `proposed` (needs a definition), `defined` (a human has defined it) or `deprecated`. |
| `definition` | — | Human-written. Empty only while `proposed` (E008). At least `min_definition_words` words (W101); not circular (W102); about the domain, not the code (W103). |
| `discouraged_terms` | — | List of `{term, note}`; `note` is optional and says who uses the term. |
| `examples`, `non_examples` | — | Short concrete cases that are, and are not, instances. Non-examples are the best way to mark a boundary. |
| `rules` | — | Invariants in plain language. Optionality ("at least one", "zero or one") goes here, not in cardinality. |
| `relations` | — | List of `{type, target, cardinality?}`. `type` is a core relation type or a declared extension (E005); `target` is another concept's id (E004). See below. |
| `implemented_in` | — | List of `{path, symbol?, reviewed_at?}`. `path` is relative to the project root and must exist (E009). `symbol` is text searched for in the file (W105 if missing) and narrows drift checks to nearby changes. `reviewed_at` is set only by `onto.py review`. |
| `open_questions` | — | What nobody knows yet. Better than guessing. |
| `proposal` | — | Agent-written, while `proposed`: `rationale` (why the concept was raised) and an optional `suggested_definition`, which the explorer shows apart from the definition. Remove it once the concept is defined. |
| `replaced_by` | — | For a deprecated concept that was renamed or merged: the id that replaces it (I202 if missing). |

### Relations and cardinality

A relation reads from this concept (the source) to `target`. Cardinality is optional
and reads source:target: `1:1`, `1:N`, `N:1` or `N:M`. On Customer,
`{type: has, target: order, cardinality: "1:N"}` means one customer has many orders.

- Leave it out when it is meaningless or unknown; a missing cardinality is never flagged.
- Not allowed on `is_a` or `attribute_of` (E013). On the symmetric `related_to`, only
  `1:1` or `N:M` (E013).
- State a relationship once. The same relationship with two different cardinalities
  (for example `related_to` written on both concepts) is E014.
- Record the domain, not a table's grain; when they differ, add an open question.

Relations also must not loop through an acyclic type such as `is_a` or `part_of`
(E006), should join concepts of the same kind under `is_a` (W111), and must respect a
relation type's `from`/`to` kinds (W110).

## Manifest (`ontology.yaml`)

```yaml
schema_version: 1
name: Acme Analytics
description: Domain concepts for the Acme analytics warehouse.
extensions:
  kinds:
    rule:
      status: defined
      definition: >
        A business policy or constraint the domain must obey.
  relation_types:
    measures:
      status: defined
      definition: >
        The source metric is computed from instances of the target.
      inverse: measured_by
      acyclic: false
      from: [metric]
      to: [entity, event]
    derived_from:
      status: proposed
      definition: ""
      inverse: source_of
      proposal:
        rationale: "Several metrics are computed from other metrics."
settings:
  stale_proposal_days: 30
  min_definition_words: 8
  drift_context_lines: 3
```

| Field | Meaning and rules |
|---|---|
| `schema_version` | The record format. This skill reads `1`; any other value stops every command with advice. |
| `name`, `description` | Shown in the explorer's toolbar and title. |
| `extensions.kinds.<id>` | `status` (required), `definition` (human-written; required once `defined`, E011), `proposal.rationale`. |
| `extensions.relation_types.<id>` | As above, plus `inverse` (required: the label read from target to source), `acyclic` (forbid loops), `from` and `to` (allowed source and target kinds; E012 if a kind is unknown). |
| `settings.stale_proposal_days` | A proposal older than this (by git date) is W107. |
| `settings.min_definition_words` | Shorter definitions are W101. |
| `settings.drift_context_lines` | How close to a symbol a changed line must be to count as drift (W106). |

Extension ids are snake_case, may not reuse a core id, and may not be declared twice or
as both a kind and a relation type (E010). The core vocabulary itself is built in and
cannot be declared or redefined in the manifest.
